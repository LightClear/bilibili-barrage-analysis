# 未解决问题、风险与后续优化清单

审查日期：2026-06-01

本文只保留当前仍未解决、仍有风险或值得继续优化的内容。已经完成的安全、性能、AI、任务系统、MySQL 预备和前端分块改进，已迁移到 `README.md` 的“已完成的优化与安全改进”章节，不在本文重复展开。

项目定位仍是课程 DEMO 和本地演示系统。当前版本已经比普通静态可视化作业完整很多，但若要接近真实可部署应用，还需要继续处理下面的问题。

优先级定义：

- P0：真实部署前必须处理。
- P1：强烈建议近期处理，会明显提升可靠性、可维护性或数据正确性。
- P2：性能、算法或体验优化，适合后续迭代。
- P3：功能扩展，适合作为长期规划。

## 一、总体剩余风险

1. 数据层仍是文件模式：账号、热门归档、弹幕、AI 配置和缓存主要依赖本地文件。虽然已有原子写入和线程锁，但没有数据库事务、查询索引、审计日志和多进程共享能力。
2. Session 管理已抽出 `SessionStore`，但默认仍是单进程内存：服务重启即失效，多进程或多机器部署无法共享。
3. 大数据能力仍有限：百万弹幕场景下，前端内存、图表计算、全量 JSON 加载和 AI 输入摘要仍可能成为瓶颈。
4. AI 结果仍需加强可验证性：模型能做语义合并，但仍需要更严格的证据校验、报告保留策略和结果版本管理。
5. 前端主页面已完成主要低风险分块，但仍是普通 `<script>` 顺序加载，长期最好改为更明确的模块接口。
6. 自动化测试已补 HTTP smoke 和前端资源结构检查，但真实浏览器 E2E、视觉回归和性能压测还没有形成体系。

## 二、P0：真实部署前必须处理

### P0-1：文件存储需要迁移到 MySQL 或等价数据库

当前文件模式适合课程展示，但不适合多人长期使用。

问题：

- `data/accounts.txt` 无法提供数据库事务、权限审计和复杂查询。
- 弹幕数据越来越大后，按文件加载会拖慢首屏和查询。
- AI Provider、用户屏蔽词、自定义榜单和历史记录分散在多个文件中，后续回档和迁移成本会上升。

建议：

- 先实现 `STORAGE_BACKEND=file|mysql` 的切换框架，默认继续使用 `file`。
- 以账号、视频、弹幕、AI 报告、任务、审计日志为第一批 MySQL 表接入对象。
- 文件模式到 MySQL 先做 dry-run 校验，再允许 owner 确认写入。
- 保留文件导出能力，确保 MySQL 测试失败时仍能回到稳定演示版本。

参考文档：

- `database/mysql/001_schema.sql`
- `database/mysql/README.md`
- `docs/database_migration_plan.md`

### P0-2：Session 与 CSRF Token 需要持久化

当前 Session、CSRF Token 和演示身份已经从 `server.py` 的散落字典抽到 `src/session_store.py`。`MemorySessionStore` 记录账号、CSRF Token、演示身份、创建时间、最近访问时间和过期时间，结构已经对齐后续 MySQL `sessions` 表。

当前仍未解决的是：默认后端还是单个 Python 进程内存。

问题：

- 服务重启后所有用户需要重新登录。
- 多进程或多机器部署时无法共享会话。
- 内存清理仍依赖请求触发，没有独立会话清理任务。

建议：

- MySQL 接入后优先实现同接口的 `MySQLSessionStore`，把 Session 写入 `sessions` 表，保存 `created_at`、`expires_at`、`last_seen_at`。
- MySQL/Redis 等持久化后端只保存 Session Token 和 CSRF Token 的 hash，不保存原始 token。
- CSRF Token 和 Session 一起持久化和过期清理。
- HTTPS 部署时 Cookie 增加 `Secure`。
- 高权限操作可增加二次确认 Token 或短期操作验证码。

### P0-3：真实 API Key 需要更强密钥管理

当前 `data/secure/` 已做本机加密存储，适合本地 DEMO，但不是生产级密钥系统。

问题：

- 如果 `server_secret.key` 和 `api_providers.json` 同时泄露，仍可能被离线解密。
- 用户自带 API 的真实余额无法由本项目可靠读取，费用仍需要用户到模型平台控制台查看。

建议：

- 真实部署使用系统 Keyring、KMS、云密钥服务或数据库字段级加密。
- 当前不再继续扩展 AI 使用统计、额度读取或调用次数管理；如果未来开通公益 API，再单独设计限流、计费提示和审计策略。
- 日志中禁止写入完整 API Key、完整请求体和完整第三方错误体。

### P0-4：公网部署需要完整安全配置

当前响应头和 CSRF 已有基础保护，但仍缺少完整部署级配置。

建议：

- 全站 HTTPS。
- Cookie 增加 `Secure`。
- 使用反向代理提供 gzip/br 压缩和静态资源缓存策略。
- CSP 继续收紧，减少对 CDN 的依赖，或把 ECharts 本地化。
- 管理员和 owner 操作写入审计日志。
- 管理员高危操作增加二次确认。

## 三、P1：近期建议处理

### P1-1：继续拆分 `app.js`

当前已完成：

- `app-core.js`：常量、DOM 工具、请求封装、格式化、任务进度面板。
- `app-video-store.js`：视频查找、弹幕池索引、搜索历史、自定义榜单、搜索缓存释放、当前视频入口。
- `app-charts.js`：统计缓存、ECharts 初始化、当前视频图表、发送时间分布、用户贡献榜、对比图表。
- `app-ai.js`：AI 模式、AI 要求、AI 数据摘要、当前视频/对比 AI 评价、AI 词云回写。
- `app-import-export.js`：数据导出、导入白名单清洗、导入确认、导入问题报告。

当前状态：

- 主页面低风险 JS 分块已经完成五轮，`app.js` 约 1090 行。
- 继续拆分并非当前最高收益项。若继续，应先补前端 E2E，再考虑 `app-search.js`、`app-compare.js`、`app-filters.js`。

新增注意点：

- 当前仍使用普通 `<script>` 顺序加载，`app-ai.js` 会在运行时调用页面中的 `currentVideo()`、`getVideoStats()`、`getCachedWordStats()`、`renderWordChart()` 等函数。
- 这种方式对当前 DEMO 是保守且可运行的，但长期最好把这些依赖整理成明确的 `window.AppState` 或轻量模块接口，降低脚本顺序和全局变量耦合。

### P1-2：静态榜单和导入数据的词频仍可能使用前端兜底

当前 BV 搜索结果已经由后端返回单视频统计，前端会在屏蔽词签名一致时优先使用服务端词频、视频内时间分布、长度分布和用户排行。但静态热门榜单、归档导入数据和旧格式 JSON 仍可能走前端 `tokenizeDanmaku()` 兜底。

剩余问题：

- 静态 dashboard 目前没有为每个视频保存单视频统计，只保存整体汇总。
- 用户导入的旧 JSON 没有 `stats` 字段时，仍需要前端本地统计。
- 前端轻量切词与后端 jieba 分词仍可能产生不同词云。

建议：

- 后续如果要彻底统一，可在导出 `dashboard.json` 时为热门视频追加按视频拆分的轻量统计索引。
- 导入 JSON 时允许读取可选 `stats` 字段，但继续保留本地兜底。
- 不建议为了统一词频而在前端引入大型分词库，当前离线兜底的收益仍高于完全一致性。

### P1-3：AI 输出仍可继续增强证据校验

当前已经限制 JSON 返回和词条数量，并已加入 `analysis_prompt_version`、`local_stats_version`、版本化缓存 key 和 artifact 保留策略。仍可继续提高的是模型输出和证据之间的可验证性。

建议：

- `words.name` 必须能在候选词、短句候选或样本弹幕中找到证据，或能由多个证据短语合并解释。
- `summary`、`keywords_comment`、`reason` 设置明确长度上限。
- 后续可以把证据校验结果写入报告元数据，例如每个 AI 词条关联的候选词、短句或样本弹幕数量。

### P1-4：B 站历史弹幕补抓仍不可保证全量

历史补抓依赖 B 站接口和用户 Cookie，有稳定性和合规边界。

当前已完成：

- 历史补抓会返回 `history_error_type`，可区分未配置 Cookie、Cookie 可能失效、接口 412/风控、索引为空、索引失败、快照失败、解析异常和达到行数上限。
- 页面仍保留“不承诺全量”的采集诊断。

剩余问题：

- Cookie 失效会导致历史补抓失败。
- B 站接口策略可能变化。
- 历史快照不是严格的“全量数据库导出”，仍可能有缺口。

建议：

- 保留当前诊断信息，不要向用户承诺“必定全量”。
- 下载历史快照时加入更明确的重试和退避。
- 后续 MySQL 接入后，记录每次补抓来源、日期范围和覆盖比例。

## 四、P2：性能与体验优化

### P2-1：全量 JSON 加载会成为瓶颈

当前首屏仍读取：

- `web/data/dashboard.json`
- `web/data/danmakus.json`

建议：

- 首页只加载榜单摘要。
- 点击视频时按 `bvid/cid` 加载对应弹幕。
- 归档数据按日期拆分。
- 浏览器端可使用 IndexedDB 缓存已查看视频。
- 服务端增加 `/api/danmakus?bvid=...&cid=...`。

### P2-2：搜索结果可升级为虚拟滚动

当前分页已经能避免一次性写入大量 DOM。如果后续希望连续浏览数万条结果，可以再升级。

建议：

- 只渲染可视区域和上下缓冲区。
- 筛选条件变化时先计算总数和摘要，再按需渲染可视行。
- 保留当前分页作为简单稳定模式。

### P2-3：视频对比需要归一化指标

当前对比主要看总量，长视频和短视频之间可能不公平。

建议增加：

- 每分钟弹幕数。
- 每千播放弹幕数。
- 点赞率、投币率、收藏率。
- 峰值分钟占全片位置百分比。
- Top 用户集中度。

### P2-4：用户弹幕贡献榜可以增加集中度指标

当前只展示 `user_hash` 计数。

建议增加：

- Top 1 用户占比。
- Top 10 用户占比。
- 用户数 / 弹幕数。
- HHI 或 Gini 集中度。

### P2-5：词云建议展示双通道

当前 AI 语义词云会覆盖当前视频词云视觉结果。用户可能希望同时看到原始统计依据和 AI 合并结果。

建议：

- 字面高频：程序稳定统计，便于复核。
- 语义主题：AI 合并后的主题，便于理解。
- 两者并列或用 Tab 切换。

### P2-6：本地兜底词云仍偏弱

没有真实模型时，本地词云仍可能出现二字切片和无意义词。

建议：

- 本地兜底也尽量复用 `jieba` 或服务端分词结果。
- 增加项目级停用词表和短语词典。
- 对“许愿”“不歪”“还愿”“出必还愿”等高频语义短语做规则增强。

## 五、P3：功能扩展方向

### P3-1：管理员后台扩展

可补充：

- 最近操作日志。
- 热门刷新历史。
- 当前任务队列。
- 用户禁用原因。
- 重置用户密码。
- 导出账号列表。

### P3-2：API 版本化

当前接口路径清晰，但后续真实接入时建议统一版本化：

```text
/api/v1/search
/api/v1/videos/{bvid}
/api/v1/danmakus
/api/v1/ai/analyze
/api/v1/admin/users
```

响应格式建议统一为：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "request_id": "..."
}
```

### P3-3：报告导出

可以把当前视频或对比视频生成报告：

- Markdown。
- PDF。
- PNG 图表截图。
- JSON 原始分析数据。

报告内容可包含视频基础信息、弹幕时间分布、长度分布、用户贡献榜、高频词云、AI 评价和对比结论。

### P3-4：更多弹幕分析能力

可扩展：

- 情绪分类：积极、吐槽、疑问、催更、许愿、玩梗。
- 主题聚类：剧情、角色、音乐、画面、运营、抽卡等。
- 弹幕复读检测：相同或近似弹幕的传播速度。
- 峰值原因解释：结合峰值分钟的弹幕样本自动总结。
- 多视频系列分析：同一 UP 或同一主题视频之间的弹幕变化。

## 六、测试与质量保障缺口

当前 Python 单元测试已经覆盖主要后端逻辑，并已增加：

- HTTP smoke 测试：静态页面安全头、登录 Cookie、CSRF 拦截、普通用户拒绝管理员接口。
- 前端资源结构测试：主页面分块 JS 顺序和登录页关键资源存在性。
- 历史补抓分类测试：`auth_required`、`index_empty`、`risk_control` 等。
- AI artifact 测试：缓存 key 随版本变化、报告保留策略不误删缓存和统计文件。

仍缺少以下测试：

1. 前端 E2E：用 Playwright 测试热门榜切换、BV 搜索、对比、AI 按钮、登录/个人页。
2. API 集成测试：mock B 站接口和 mock 模型服务，避免真实网络影响测试稳定性。
3. 性能测试：构造 1 万、5 万、10 万条弹幕，测试筛选、图表、导入和 AI 摘要耗时。
4. 视觉回归：保存关键页面截图，避免布局调整破坏榜单、对比图、个人页和 AI 面板。
5. 数据兼容测试：旧版导出 JSON、缺字段视频、多 P 视频、空弹幕视频。

## 八、结论

当前已完成的改进已经覆盖 DEMO 级安全、任务进度、AI 接入、缓存、账号权限、会话封装、主页面分块、HTTP smoke 测试、历史补抓分类和 AI artifact 保留策略。本文保留的问题集中在 MySQL 数据层、多用户持久化、大数据性能、AI 证据可信度和真实浏览器测试体系上。下一步不建议继续堆界面功能，应优先进入 MySQL 前置接入和持久化会话设计。
