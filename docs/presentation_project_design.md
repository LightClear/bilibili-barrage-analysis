# 项目设计文档

## 项目定位

本项目面向课程展示和本地数据分析场景，目标是把 B 站视频弹幕从“原始文本列表”整理成可交互、可对比、可解释的数据工作台。系统不是只生成一组静态图表，而是支持从热门榜单浏览、单个 BV 搜索、弹幕筛选、视频对比到 AI 评价的连续操作。

## 设计背景

B 站弹幕具有强实时性和强语境性。单独查看弹幕文本很难回答下面的问题：

- 某个视频的观众互动集中在哪些时间段。
- 弹幕中最常出现的词语、短句和情绪倾向是什么。
- 不同视频之间的互动强度、关键词和观众表达方式有什么差异。
- 热门榜单在不同日期下的数据能否快速切换和归档查看。
- 本地运行时如何避免弹幕文件和缓存无限增长。

因此项目设计重点放在三个方向：数据采集与归档、交互式可视化、可控的本地储存。

## 用户与角色

| 角色 | 主要能力 | 设计目的 |
| --- | --- | --- |
| 普通用户 | 查看热门榜单、搜索 BV、筛选弹幕、查看图表、导入导出 | 覆盖基本分析需求 |
| API 用户 | 在普通用户基础上启用 AI 分析 | 用户自带模型 Key，降低项目内置成本 |
| 管理员 | 刷新热门榜单、管理普通账号、维护全局屏蔽词、清理缓存和储存 | 支持本地运维和展示控制 |
| owner | 继承管理员能力，并维护管理员权限和全局 AI 使用统计 | 防止普通管理员越权修改高权限账号 |

## 核心功能设计

### 热门榜单

热门榜单默认采集 B 站热门前 50 个视频，并按日期归档。页面支持最近 14 天归档切换，历史归档保持只读。

设计要点：

- 榜单本身只加载视频列表、排名、展示指标和单视频统计。
- 弹幕明细不跟随榜单一起全量加载。
- 用户点击视频、加入对比或触发 AI 分析时，再按需加载该视频自己的弹幕 JSON。
- 榜单使用原生滚动列表展示，适合 50 条长标题和高频点击浏览。

### BV 视频搜索

BV 搜索可能遇到长视频、多分 P、历史弹幕补抓和网络等待。项目将搜索改成后台任务：

- 前端调用 `/api/jobs/search` 创建任务。
- 后端采集视频信息、分 P、弹幕和统计结果。
- 前端轮询 `/api/jobs/status` 展示进度。
- 成功后通过 `/api/jobs/result` 获取完整结果。

这样页面不会长时间停留在“正在获取”，用户可以看到当前处理阶段、进度和诊断信息。

### 弹幕分析视图

当前视频分析包括：

- 视频基础信息和弹幕采集诊断。
- 视频内弹幕时间分布。
- 弹幕发送时间分布。
- 弹幕长度分布。
- 高频关键词和词云。
- 用户贡献榜。
- 弹幕筛选结果。

这些图表优先复用后端返回的单视频统计。当账号屏蔽词变化或弹幕池变化时，前端会清空缓存并重新计算，避免图表和弹幕列表不一致。

### 视频对比

用户可以把热门榜单、搜索历史或自定义榜单中的视频加入对比。对比视图关注：

- 弹幕数、播放量、点赞、硬币等指标差异。
- 时间分布峰值差异。
- 关键词差异。
- AI 对比评价。

对比列表不参与导出，避免导出文件携带过多临时状态。需要对比时可以从视频详情重新加入。

### AI 评价

AI 评价统一走 `/api/ai/analyze`。系统支持三种模式：

- 省钱模式：提交本地统计摘要和代表弹幕，适合日常使用。
- 深度摘要：提交更多样本和峰值片段，分析更细。
- 全量原文：用户确认后最多提交 20000 条弹幕，适合需要更完整上下文的场景。

AI 分析支持缓存和重新分析。同账号、同模型、同模式、同数据和同分析要求会优先命中缓存。模型失败时回退到本地分析，保证页面流程不中断。

### 账号中心与管理员页

账号中心承担三个职责：

- 普通用户资料、API 开关、个人屏蔽词和 B 站历史补抓凭证配置。
- 模型 Provider 配置，账号级加密保存 API Key。
- 管理员界面，包括榜单刷新、用户管理、全局屏蔽词、AI 缓存和本地储存清理。

管理员功能不是完整后台系统，但接口边界已经按照后续数据库替换进行预留。

## 交互设计原则

- 首屏进入实际工作台，不做单纯展示型落地页。
- 榜单、当前视频、筛选、图表和对比形成连续工作流。
- 长任务必须有进度反馈。
- 大弹幕文件按需加载，不让日期切换承担全量弹幕成本。
- 搜索历史最多保留 15 个未固定视频，避免前端内存无限增长。
- 文件清理提供预览和确认机制，降低误删风险。

## 关键设计决策

### 弹幕按视频拆分，而不是全量加载

早期方案在切换榜单时会读取整份 `danmakus.json`，导致首次加载和日期切换卡顿。当前设计把弹幕拆成：

- 当前榜单的 `danmaku_index.json`
- 当前榜单的 `video_stats.json`
- 每个视频自己的 `danmakus/<BVID>.json`

页面切换榜单只读取轻量榜单快照和统计数据。弹幕明细只在真正使用某个视频时加载。

### 后台任务替代同步等待

热门榜单刷新和 BV 搜索都可能耗时较长。使用内存任务表后，用户可以看到进度，接口也不会阻塞其他请求。后续接入 MySQL 时，可以把任务状态迁移到 `jobs` 和 `job_events` 表。

### 文件模式优先，数据库结构预留

课程项目和本地运行更重视可部署、可检查和低依赖，因此主流程仍使用 JSON 文件。但是项目已经准备 MySQL 表结构、迁移工具和导入导出工具，后续可以逐步替换账号、弹幕、统计和任务储存。

### AI 先做本地摘要，再交给模型

直接把大量弹幕全部提交给第三方模型成本高、延迟长，也有上下文长度限制。当前方案先在前端和后端做统计摘要，再让模型基于证据输出评价和语义词云。这样既控制成本，也能在没有模型 Key 时回退到本地分析。

## 可展示亮点

- 将弹幕数据从原始文本转换为可浏览、可筛选、可对比的分析工作台。
- 热门榜单支持按日期归档和快速切换。
- 弹幕拆分储存与按需加载明显降低卡顿。
- BV 搜索任务有进度可视化和采集诊断。
- AI 分析不是单纯聊天，而是结合词频、峰值、代表弹幕和缓存策略。
- 账号权限、CSRF、加密保存 Key、屏蔽词隔离和本地储存清理形成完整工程闭环。

## 当前边界

- 默认仍是本地文件模式，不是生产级数据库服务。
- Session 当前保存在进程内存，服务重启后需要重新登录。
- 历史弹幕补抓依赖 B 站接口和 Cookie 状态，不能保证所有老视频都拿到完整历史弹幕。
- `/api/search` 旧同步接口仍保留兼容，主页面已优先使用后台任务。
- MySQL 表结构和迁移工具已准备，但尚未接管主业务流程。
